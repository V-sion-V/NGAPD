# M0：领域基线和工程骨架需求

- 功能 ID：`m0-domain-baseline`
- 文档状态：已澄清，等待独立规划
- 确认日期：2026-07-27

## 1. 背景与目标

NGAPD 已完成产品与架构基线以及 Workspace Sync、Task UI、Agent Context 三个前置原型，并已将原型工作流封存为 `completed/passed`。M0 的目标不是继续扩充原型，而是把已验证的工程骨架和产品文档中的核心领域约束收敛为可执行、可迁移、可验证的服务端基础，使 M1“项目、角色和成员”与 M2“任务管理闭环”无需重新发明底层规则。

M0 面向后续服务端应用服务、Web、Workspace CLI、Worker 和共享契约的实现者。完成后，即使没有正式任务管理 UI，也必须能通过领域、数据库和 API 契约证据证明任务树、有效 Owner、同级依赖图、状态、冻结、重新打开、影响集合和 Workspace 协调等核心不变量。

目标结果：

- 建立唯一的正式领域语义、模块边界、数据库基线和迁移方式。
- 使 Project Key、Task Key、任务树、同级 DAG、状态与 Workspace 生命周期具备可复用实现契约。
- 用真实 PostgreSQL 并发边界证明图版本、移动、依赖和冻结不会产生半提交或非法结构。
- 统一 `/api/v1`、运行时 Schema、错误码、审计、Outbox、SSE 和工程门禁约定。
- 保持现有 Identity、Workspace、Web、Workspace CLI 与原型证据可用，为 M1/M2 提供稳定入口。

## 2. 范围

### 2.1 包含范围

- 模块化单体边界、模块间调用规则、共享契约边界和版本化迁移框架。
- 可丢弃原型数据库的显式破坏性重建，以及从空 PostgreSQL 数据库可重复建立 M0 正式基线。
- 全局唯一、不可变的 Project Key，以及项目内事务性单调分配且不复用的 Task Key。
- 任务邻接树、虚拟项目根、显式 Owner、最近祖先继承的有效 Owner和异常 Owner 解析。
- 每父级同级 DAG、`graph_version`、跨 Owner 依赖变更请求与接受、陈旧请求失效。
- 任务关注、基础/有效状态、人工阻塞、完成资格、完成冻结、重新打开 `deny / cascade` 策略和影响集合。
- 移动任务对源/目标图版本的稳定顺序锁定，以及与依赖增删共享的并发互斥边界。
- 统一 API 版本、运行时校验、幂等、乐观并发、错误响应和不可变审计写入接口。
- 最小 Workspace 服务端契约：作用域唯一性、`sync_version`、独占租约、工作周期、冻结、快照和任务生命周期协调端口。
- Fastify/TypeBox/Kysely/OpenAPI、PostgreSQL 递归与并发、Graphile Worker/Outbox、对象一致检查点、Workspace 核心平台端口和 SSE 的 M0 验证结论。
- Web、API、Worker、Workspace CLI、共享包、数据库迁移和 Docker Compose 的最小持续集成与可发布构建门禁。

### 2.2 不包含范围

- 不提供完整的 Project、Membership 或 Task 公共 HTTP CRUD；这些用户流程分别属于 M1 和 M2。
- 不新增正式任务管理 UI；M3 才交付平铺树状任务界面。
- 不实现 macOS/Windows Workspace 本地物化、文件监听、真实目录同步或可选 GUI；这些属于 M4。M0 只固定平台端口和服务端契约。
- 不注册 Agent 任务修改工具、不实现操作提案 UI 或完整 Agent Skill；这些属于 M5。
- 不交付 Wiki、全文搜索用户流程、正式项目备份/恢复入口或摘要闭环；这些属于 M6。M0 仅验证对象清单与一致检查点的技术可行性。
- 不发布公共 npm 包、公共容器镜像或签名安装包。
- 不建设微服务、Redis、独立消息队列、独立搜索服务、独立对象存储、Kubernetes、高可用或跨地域容灾。
- 不保留当前原型数据库实例中的业务记录；用户已明确这些实例均可丢弃。

## 3. 已确认的项目事实与约束

- 仓库使用 Node.js 24、pnpm 11 和 TypeScript 单仓库；主要包为 `apps/api`、`apps/worker`、`apps/web`、`apps/workspace-cli`、`packages/domain`、`packages/contracts`、`packages/database`、`packages/object-store`、`packages/workspace-core` 和 `packages/test-fixtures`。
- 服务端采用 Fastify 模块化单体和 PostgreSQL/Kysely；HTTP 应用与 Worker 是独立进程，但共享正式领域和契约。
- Web 使用 React/Vite；Workspace CLI 通过 MCP stdio 提供当前只读状态与诊断能力，共享核心不得依赖 CLI 人类文本。
- 当前仓库已经存在 `/api/v1`、OpenAPI 3.1、请求 ID、基础稳定错误码、审计表、Identity/设备配对，以及 Workspace 清单、对象、租约、同步版本和冲突处理实现。
- 当前数据库和 Task 契约仍包含原型骨架语义，例如 `open / in_progress / done / archived` 状态与较宽的 Project Key 规则；正式基线以领域文档中的 `not_started / in_progress / done`、独立归档生命周期和 `[A-Z]{2,6}` Project Key 为准。
- 当前正式领域代码只覆盖部分有效 Owner、Workspace 授权、配对和租约规则；任务树、正式 DAG、状态、冻结、重新打开、影响集合和图并发尚未形成生产领域闭环。
- 每个任务最多一个有效 Owner；子任务显式 Owner 可空并继承最近一个显式 Owner 非空祖先，顶层任务必须有活动显式 Owner。完成继承 Owner 的任务时必须先固化该 Owner。
- 任务依赖只允许连接同项目、同一直接父级作用域的启用任务；顶层任务属于虚拟项目根作用域。每个作用域拥有独立 `graph_version`。
- 已完成任务冻结内容、Owner、结构、依赖、阻塞和任务级 Workspace；只保留评论、显式重新打开和已完成顶层归档等明确例外。
- 三种 Workspace 均以服务端为权威，使用独占写入租约和单调 `sync_version`；任何角色、管理员模式或 Agent 确认都不能绕过单写者、版本和路径保护。
- 全部业务数据自托管；NGAPD API 与 Worker 运行时不得调用外部 API、AI 或 LLM，也不得向外部服务发送业务内容。
- 初期目标是少于 10 名用户、单项目按 5,000 个活动任务、树深按 20 层、单父级按 200 个直接子任务验证；这些规模值不是领域硬限制。
- 现有 `/api/v1` Identity 与 Workspace 调用方属于兼容边界；尚未被正式路由消费的 Task 原型 Schema 可以在 M0 收敛为正式语义。
- M0 的 Agent 流程文档位于 `docs/requirements/m0-domain-baseline/`，并采用 schema `3.2` 工作流。
- 跨后续阶段必须持续保持：数据库权威、服务端重新授权、租户过滤、单写 Workspace、不可变 Task Key、同级无环依赖、冻结边界、稳定错误码、秘密不入日志、仓库可构建。

## 4. 交付与验证策略

本次初始运行采用用户明确选择的 `relaxed` 策略：

- 实现可以先于测试，不要求为每项变化强制取得 red-first 证据。
- 所有 `core` 验收、项目硬门禁、安全、隐私、数据完整性、公共兼容性、可构建性和恢复安全仍然阻塞完成。
- 仅当独立证据证明不影响已交付行为时，`supplemental` 异常才可作为带严重程度的 `FND-I-*` 报告项保留。
- `critical`、`high`、影响安全/隐私/数据/兼容性/构建运行、影响未知、违反硬门禁或未独立证明 core 结果的问题不得报告后通过。
- 验收项目一旦失败，不得为了完成运行而从 `core` 降级为 `supplemental`。

## 5. 功能需求

- `FR-001`：服务端必须维持 Identity、Projects/Membership、Roles、Tasks、Dependency Graph、Authorization/Audit、Workspaces、Agent Operations、Knowledge/Notifications 的模块归属；模块之间必须通过应用服务、只读接口或领域事件协作，不得跨模块直接更新他方数据表。
- `FR-002`：M0 必须建立可从空 PostgreSQL 数据库重复执行的正式迁移基线。当前原型实例的数据不要求保留，允许删除、重命名或重建原型表和字段，但破坏性重建必须显式、可诊断、文档化，不得伪装为无损升级。
- `FR-003`：Project Key 必须匹配 `[A-Z]{2,6}`、全局唯一、创建后不可修改且归档后不释放；内部关联必须使用不可猜测主键，不得使用 Project Key 代替引用完整性。
- `FR-004`：Task Key 必须由不可变 Project Key 与项目内事务性单调 `Sequence` 组成；允许间隙但不得复用。并发创建与幂等重试不得产生重复编号或为同一请求分配多个任务。
- `FR-005`：任务必须以同项目邻接树存储；父任务不得是自身或后代，跨项目父子关系必须拒绝。顶层任务归属虚拟项目根并必须保存活动显式 Owner。
- `FR-006`：有效 Owner 必须解析为当前任务或最近祖先的活动显式 Owner；循环、孤儿父引用、跨项目祖先、缺失或失活 Owner 必须返回可诊断失败，不得猜测 Owner。继承 Owner 的任务完成时必须将当前有效 Owner 固化为显式 Owner。
- `FR-007`：启用任务的依赖只能连接同项目、同一直接父级作用域中的不同任务；同一方向边唯一，新增边后必须无环。虚拟项目根和普通父任务作用域必须使用相同的同级 DAG 语义。
- `FR-008`：每个普通父任务作用域和虚拟项目根作用域必须恰有一个事务性 `graph_version`。活动依赖增删、任务移动、端点归档或删除等改变活动图事实的操作必须锁定并递增全部受影响版本。
- `FR-009`：普通模式下，拥有两个依赖端点或拥有共同直接父任务的成员可以直接修改合法依赖；只拥有一个端点时必须创建绑定端点、有效 Owner 和 `graph_version` 的变更请求，由另一端有效 Owner 接受。接受时任一事实变化都必须使请求 `stale`；顶层作用域由 Project Owner 控制。
- `FR-010`：移动任务必须按稳定主键顺序同时锁定源、目标父级图版本，在锁内重新检查任务没有活动依赖、目标未完成、父子无环和权限有效；移动与依赖增删必须共享互斥边界，成功时源和目标图版本均递增。
- `FR-011`：关注只能连接同项目的两个不同任务且同向唯一，可以形成环；它只能提供一跳发现，不得改变 Owner、权限、依赖、阻塞、完成、图版本或 Workspace 写入资格。
- `FR-012`：任务基础状态必须为 `not_started / in_progress / done`；`blocked` 必须由未解决人工阻塞或未完成启用 predecessor 派生。父任务只在全部启用直接子任务完成后获得完成资格，不得自动完成。
- `FR-013`：任务进入 `done` 前必须重新检查有效 Owner、启用直接子任务、启用 predecessor、人工阻塞、权限和相关版本；完成必须与 Owner 固化、任务级 Workspace 最终服务端版本、完成快照、冻结和审计处于同一原子业务边界。
- `FR-014`：完成后必须冻结标题、正文、截止时间、逻辑角色、标签、展示类型、Owner、结构、依赖、阻塞和任务级 Workspace。评论、显式重新打开和已完成顶层归档是明确例外，不得由低层入口绕过冻结。
- `FR-015`：重新打开必须将目标恢复为 `in_progress` 并为任务级 Workspace 创建新工作周期，保留旧快照和摘要。已完成祖先必须先处理；`deny` 必须拒绝存在已完成 successor 的操作，`cascade` 必须准确包含全部已完成 successor 闭包，跨 Owner 影响要求管理员能力和完整影响确认。
- `FR-016`：移动、顶层归档、非顶层删除、显式 Owner 变化、级联重新打开和关注变化必须先计算确定性影响集合；适用时必须覆盖目标及后代、失效依赖、有效状态变化、已完成祖先、活动租约、未同步版本和父级图版本。
- `FR-017`：领域授权接口必须以服务端解析的用户、Membership、Project Owner、有效 Task Owner、管理员会话和影响集合为事实来源。确认不得替代授权；所有租户查询必须包含服务端解析的 `project_id`。
- `FR-018`：所有 M0 公共 HTTP 接口必须位于 `/api/v1`，使用 TypeBox 运行时校验并进入 OpenAPI 3.1。创建、确认执行和同步提交等可重试操作必须支持幂等；资源写入必须使用资源版本、`graph_version` 或等价条件。
- `FR-019`：HTTP 错误响应必须包含稳定机器码、用户可读信息、请求 ID，并在适用时包含当前版本和可执行恢复建议；内部领域/应用失败必须能够无歧义映射到同一错误目录。验证、权限、冻结、图版本、陈旧请求、依赖环、租约和幂等冲突不得退化为无差别内部错误。
- `FR-020`：审计写入接口必须记录 M0 范围内关键操作的成功和失败尝试，至少包含操作者、代理类型、项目、目标、请求 ID、时间、前后版本、结果和原因；审计不得保存密码、令牌、租约秘密或不必要的 Workspace 全文。
- `FR-021`：每个用户、项目和任务必须通过 `(scope_type, scope_id)` 恰有一个逻辑 Workspace。Workspace 必须具有独立生命周期、单调 `sync_version`、单调工作周期、不可变版本/快照和每工作周期最多一个有效写租约。
- `FR-022`：M0 必须为任务完成、重新打开、Owner 变化、冻结、快照和租约撤销提供 Workspace 应用端口与事务协调边界，并用服务端契约证明不会留下“任务已变而 Workspace 未变”或相反的半状态；M0 不要求本地物化。
- `FR-023`：Workspace 授权模型必须保留产品基线：用户级本人写、项目级 Project Owner/Admin 写、任务级有效 Task Owner 写；任何写入仍需有效唯一租约。读取与 Agent 额外意图限制必须保持为可独立表达的策略，不得由写权限或管理员模式隐式扩大。
- `FR-024`：现有 `/api/v1` Identity 和 Workspace 正式行为必须保持兼容；若为正式领域语义修正 Task 原型 Schema，必须同步更新共享契约与调用测试，不得静默改变已发布 Identity/Workspace 输入输出。
- `FR-025`：M0 必须完成 ADR 指定的六类验证并留下可判定结论：Fastify/TypeBox/Kysely/OpenAPI 链路，递归 CTE/稳定锁/并发夹具，Graphile Worker/Outbox 事务交接，对象清单与一致检查点，Workspace 核心平台端口，SSE 游标与断线重连。验证否定既有选择时必须新增替代 ADR，不得静默换型。
- `FR-026`：共享包必须提供运行时契约、领域枚举和错误码，但 Web、Workspace CLI 和其他客户端不得导入服务端领域服务或数据库实现；生产领域规则不得只存在于 UI、测试夹具或文档中。
- `FR-027`：最小持续集成与发布门禁必须覆盖仓库格式、静态检查、构建、类型检查、自动化测试、数据库迁移验证，以及 Docker/Compose 构建和健康启动证据；M0 不要求向公共注册表发布制品。
- `FR-028`：M0 不得提前暴露完整 Project/Task CRUD、正式任务 UI、本地 Workspace 同步或 Agent 写工具。内部应用接口和测试入口必须能被 M1/M2 复用，但不得成为绕过未来授权与确认的临时公共入口。

## 6. 用户流程或调用流程

### 6.1 建立干净数据库基线

1. 开发者明确选择 M0 原型数据库重建流程。
2. 系统警示当前记录会被销毁，并拒绝把该流程描述为数据保留升级。
3. 迁移器从空 PostgreSQL 数据库建立正式 Schema、约束和初始元数据。
4. 再次执行迁移时不重复创建数据对象，也不产生漂移。
5. 应用、Worker 和健康检查使用同一 Schema 版本启动。

### 6.2 分配 Project Key 与 Task Key

1. 内部应用服务接收经过规范化和授权的创建意图与幂等键。
2. Project Key 经格式、全局唯一和不可变规则校验。
3. 创建任务时，服务在项目事务中分配下一个 Sequence，组合不可变 Task Key。
4. 并发或网络重试返回一个确定结果，不复用已经分配的编号。
5. 正式公共 Project/Task 创建路由留给 M1/M2。

### 6.3 修改同级依赖

1. 服务解析两个端点、共同直接父级、有效 Owner 和当前 `graph_version`。
2. 若当前成员拥有两端或共同父任务，直接在图事务中校验并修改。
3. 若只拥有一个端点，创建绑定当前事实的变更请求。
4. 另一端有效 Owner 接受时重新检查全部事实；版本或 Owner 改变则返回 `stale`。
5. 合法修改递增图版本、写入审计，并使并发旧请求失效。

### 6.4 移动任务与并发依赖操作

1. 服务计算移动影响集合和源/目标父级作用域。
2. 按稳定顺序锁定两个图版本。
3. 在锁内重新检查父子无环、目标状态、权限和源任务活动依赖。
4. 并发依赖增删使用相同锁边界，只能在移动前或移动后的一致父级事实上完成。
5. 成功移动递增两个图版本；失败不改变结构、依赖或任一版本。

### 6.5 完成与重新打开

1. 完成服务锁定任务和相关图事实，重新验证 Owner、子任务、predecessor、blocker、权限和 Workspace 版本。
2. 服务在同一业务边界固化继承 Owner、创建快照、冻结任务及任务级 Workspace，并写入审计。
3. 重新打开时，服务根据 `deny / cascade` 计算影响，处理已完成祖先和 successor，创建新工作周期。
4. 任一版本、Owner、租约或影响集合变化都会使旧操作失效，不得部分执行。

### 6.6 工程门禁

1. 提交触发共享的仓库质量检查和数据库集成验证。
2. 发布候选构建 API、Worker、Web、Workspace CLI 与共享包。
3. Docker/Compose 骨架完成迁移、启动和健康检查。
4. 任何 core 门禁失败都会阻止 M0 工作流完成；合格 supplemental 异常按 `FND-I-*` 记录。

## 7. 数据、接口与状态

### 7.1 关键持久化对象

- `Project`：内部 ID、不可变 `project_key`、`task_sequence`、唯一 Project Owner、`completed_successor_reopen_policy`、状态、`recovery_epoch` 和乐观版本。
- `Task`：内部 ID、项目、不可复用 Sequence/Task Key、父任务、可空显式 Owner、正文与展示字段、`base_status`、版本和独立归档事实。
- `SiblingTaskGraphVersion`：项目、普通父任务或虚拟根作用域、单调 `graph_version`，作用域组合唯一。
- `TaskDependency`：同级 predecessor/successor 唯一边及审计来源。
- `TaskDependencyChangeRequest`：动作、两端、期望图版本、请求者、必要接受者、状态与有效期。
- `TaskFollow`：同项目 source/target 唯一关系。
- `TaskBlocker`：人工阻塞及解除事实。
- `Workspace`、`WorkspaceVersion`、`WorkspaceLease`、对象与清单：保留现有服务端权威、版本和租约语义，并增加任务生命周期协调所需端口。
- `AuditEvent`、Outbox 与 Worker 作业：审计是不可变业务记录；Outbox/投影可重建，不是业务权威状态。

### 7.2 状态与版本

- 任务基础状态只保存 `not_started / in_progress / done`；`blocked` 是投影，归档是独立生命周期。
- Project Key、Task Key、已提交 Workspace 版本、完成快照和审计一经建立不得原地改写。
- Task `version` 保护内容和状态写入；`graph_version` 保护同级图与相关提案；`sync_version` 和工作周期保护 Workspace 提交。
- 依赖变更请求至少具有 `pending / accepted / rejected / expired / stale`。
- Workspace 生命周期、本地副本状态和连接/租约状态必须分开建模；M0 服务端不得引入本地副本作为权威状态。

### 7.3 接口边界

- 公共 HTTP 契约继续使用 `/api/v1`、JSON Schema、OpenAPI 3.1 和统一错误体。
- M0 新增的 Project/Task 能力默认只作为领域/应用端口、Repository 和测试契约存在，不注册完整用户 CRUD 路由。
- Worker 只消费已提交 Outbox/作业；不得承载必须与请求同步提交的领域不变量。
- SSE 只通知客户端重新获取权威资源，不承担业务提交或维持 Workspace 租约。
- Workspace 核心平台端口必须保持 UI 无关；M0 不授予真实文件系统写入、凭证或同步能力。

### 7.4 数据迁移

- 用户已明确当前数据库实例均为可丢弃的原型数据库，M0 不承担原型记录的数据转换、备份或恢复。
- 重建流程必须清楚标识破坏性，且只应用于经确认可丢弃的实例；遇到未确认可丢弃的数据库必须停止。
- 重建后的正式 Schema 必须从空库可重复创建、可由应用检测版本，并为后续前向迁移保留稳定机制。
- Git 中的原型代码、结果证据和已封存工作流不因数据库重建而删除或改写。

## 8. 异常、边界与恢复

- Project Key 格式错误、重复或修改尝试必须被稳定拒绝；Task Key 分配冲突必须在事务内重试或失败，不得返回重复 Key。
- 孤儿父节点、跨项目父子关系、树环、缺失有效 Owner、跨父依赖、自环、重复边和依赖环必须在持久化前拒绝。
- `graph_version`、Task `version`、Owner、权限或影响集合变化后，旧依赖请求、确认和结构操作必须失效并返回当前事实或恢复建议。
- 移动与依赖并发失败时必须整体回滚，不得出现任务已移动但依赖仍跨父、只递增一个图版本或审计宣称成功的状态。
- 完成条件、Workspace 最终版本、租约或快照任一失败时，任务不得进入部分冻结；重新打开失败时不得只创建新工作周期而保持任务完成。
- `deny` 重新打开必须返回阻止操作的已完成 successor；`cascade` 必须稳定计算闭包并在跨 Owner 或版本变化时拒绝旧确认。
- 对已完成任务的非法内容、Owner、结构、依赖、阻塞或 Workspace 写入必须返回稳定冻结错误；不得通过低层 Repository、批量入口或管理员模式绕过。
- Outbox/Worker 和 SSE 可以重试或断线重连，但处理器必须幂等；游标过旧时客户端必须重新获取权威状态。
- 当前数据库重建不可恢复原型业务记录。执行前必须明确目标实例可丢弃；误指向未确认实例属于阻塞错误，不得自动继续。
- M0 实现回滚以恢复代码版本并重新建立空数据库为边界，不承诺把破坏性重建后的原型数据恢复回来。
- 现有 Identity/Workspace 兼容测试失败、未知迁移半状态、无法重建空库、core 并发测试不确定或根工程无法构建时，M0 不得标记完成。

## 9. 非功能需求

### 9.1 正确性与规模

- 领域不变量、权限和数据一致性优先于吞吐量优化。
- 树算法必须按深度 20 验证递归正确性；同级 DAG 必须按 200 个直接子任务验证；项目级数据模型必须不把 5,000 个活动任务写成硬限制。
- 相关 200 节点局部 DAG 读取在参考服务器正常内网/VPN 条件下目标 P95 小于 800 ms；明显卡顿或超时属于 core 失败，未达到精确目标但不影响交付行为时可以作为 supplemental 性能发现项。未达标时优先修正查询、索引和分页，不引入缓存集群。
- 并发正确性必须由真实 PostgreSQL 事务、行锁和约束证据支持，不能只依赖内存模拟。

### 9.2 安全与隐私

- 所有项目数据访问必须使用服务端解析的租户范围；不得信任客户端提供的 Project Key 作为唯一隔离条件。
- 密码、设备秘密、访问令牌、租约令牌和管理员能力不得进入普通日志、审计元数据或错误响应。
- Workspace 内容、评论和提示文本按不可信输入处理；它们不得改变工具和服务端授权。
- NGAPD 服务端运行时不得出现外部 API、AI 或 LLM 依赖。

### 9.3 可观测性与运维

- 应用日志必须为结构化 JSON，并包含时间、级别、请求 ID、模块和稳定错误码。
- `/health/live` 与 `/health/ready` 必须继续区分进程存活和依赖就绪。
- Worker 作业必须保存失败原因、重试次数和可人工重试状态；审计日志与普通诊断日志分离。
- M0 不要求 Prometheus、Grafana、集中日志或分布式追踪。

### 9.4 构建、兼容与部署

- Node.js 24、pnpm 11、锁文件和现有 workspace 包边界保持权威。
- 现有 Identity、Workspace、Web、Workspace CLI 和三个原型的核心自动化不得回归。
- Docker Compose 继续面向单台 Linux x86-64、自托管、内网或 VPN 部署，并包含迁移、API、Worker、PostgreSQL、Gateway 和持久卷骨架。
- M0 不要求 Windows/macOS 本地同步兼容矩阵；原型已验证能力不得因共享核心改动退化。

## 10. 初步实现方向与影响范围

- 在 `packages/domain` 中建立任务标识、树、Owner、DAG、依赖请求、关注、状态、冻结、重新打开和影响集合的纯领域能力；正式规则不得留在原型夹具中。
- 在 `packages/contracts` 中统一正式枚举、API Schema、错误码、版本字段和内部应用端口的可序列化边界。
- 在 `packages/database` 中建立正式 M0 Schema、约束、迁移、Repository 和真实 PostgreSQL 并发夹具；利用唯一约束、外键、检查约束和稳定行锁顺序形成双重保护。
- 在 `apps/api` 中保持 Identity/Workspace 路由兼容，新增模块组合、错误/审计适配和必要的内部契约测试；不提前注册完整 Project/Task CRUD。
- 在 `apps/worker` 中验证 Graphile Worker 与 Outbox 的事务交接和幂等消费；业务权威状态仍由请求事务提交。
- 在 `packages/workspace-core`、`packages/object-store` 和 Workspace 服务中补齐生命周期协调端口及一致检查点验证，不增加本地真实写能力。
- 在 `packages/test-fixtures` 中复用三个原型的确定性树、DAG、Workspace 和 Agent Context 数据，但正式验收必须直接针对生产领域接口。
- 在仓库工程配置中形成统一 CI、迁移验证和 Compose 冒烟门禁，不发布公共制品。
- 主要风险是破坏性 Schema 收敛、现有 Workspace 行为兼容、跨模块事务归属、稳定锁顺序、完成/Workspace 原子边界，以及 M0 与 M1/M2 的职责越界。
- 规划阶段可以按迁移与并发风险选择合适的阶段数量和详细度，但不得修改本需求确定的产品行为、公共兼容边界或验收层级。

## 11. 验收标准

| 验收 | 层级 | 可观察结果 |
| --- | --- | --- |
| `AC-001` | core | 经明确确认的原型数据库可以被破坏性重建；从空 PostgreSQL 数据库能够建立完整 M0 Schema，重复迁移不产生重复对象或漂移，应用与 Worker 只在 Schema 就绪后报告 ready。 |
| `AC-002` | core | Project Key 只接受 2—6 位大写字母，全局唯一且不可修改；归档不释放 Key。 |
| `AC-003` | core | 同一项目的并发任务创建产生唯一、单调且不复用的 Task Key；幂等重试只返回一个任务，允许回滚造成编号间隙。 |
| `AC-004` | core | 合法任务操作后树始终同项目且无环；顶层任务始终有活动显式 Owner，子任务有效 Owner 精确来自最近活动显式 Owner 祖先，异常链返回稳定诊断。 |
| `AC-005` | core | 虚拟根和普通父任务的启用依赖均只存在于同级作用域，无自环、重复边或环；非法边在提交前被拒绝。 |
| `AC-006` | core | 每个父级作用域恰有一个单调 `graph_version`；活动图事实变化精确递增受影响版本，旧依赖请求和确认在版本或 Owner 变化后稳定成为 `stale`。 |
| `AC-007` | core | 拥有两端或共同父任务时可直接修改合法依赖；只拥有一个端点时必须由另一端有效 Owner 接受；无权、已完成端点或陈旧请求不能通过低层接口生效。 |
| `AC-008` | core | 真实 PostgreSQL 并发下，任务移动与源/目标作用域依赖增删只能按一致顺序完成；任何交错都不会产生跨父依赖、树环、单边图版本递增或半提交。 |
| `AC-009` | core | 关注只连接同项目不同任务并一跳展开；关注环不导致递归加载，且任何关注变更都不改变 Owner、依赖、状态、图版本、权限或 Workspace 写资格。 |
| `AC-010` | core | `blocked` 完全由人工阻塞和未完成启用 predecessor 派生；直接子任务完成只产生可完成资格和一次对应提示，不会自动完成父任务。 |
| `AC-011` | core | 完成操作只在 Owner、子任务、predecessor、blocker、版本和 Workspace 条件全部满足时提交；继承 Owner 被固化，任务与 Workspace 同时冻结并产生同一事实边界的快照和审计。 |
| `AC-012` | core | 已完成任务的内容、Owner、结构、依赖、阻塞和任务级 Workspace 写入均被拒绝；评论、显式重新打开和已完成顶层归档保留为明确例外。 |
| `AC-013` | core | `deny` 精确拒绝有已完成 successor 的重新打开；`cascade` 精确重新打开全部已完成 successor 闭包并创建新工作周期，旧快照保持不变，跨 Owner 或陈旧影响确认不能执行。 |
| `AC-014` | core | 移动、归档、删除、Owner 变化、级联重新打开和关注变化返回确定性影响集合；授权与确认不会遗漏适用的后代、外部依赖、有效状态、已完成祖先、租约、未同步版本或图版本。 |
| `AC-015` | core | 每个用户、项目和任务恰有一个对应逻辑 Workspace；用户级本人写且其他已认证用户只读，项目级活动成员读且 Project Owner/Admin 写，任务级活动成员读且有效 Task Owner 写；所有写入仍需唯一有效租约。`sync_version`、工作周期和不可变版本保持单调，读取策略与 Agent 额外意图限制可以独立表达。 |
| `AC-016` | core | 任务完成、重新打开、Owner 变化、冻结、快照和租约撤销的 Workspace 端口在失败注入和并发情况下不会留下任务/Workspace 半状态；不需要本地物化即可证明该契约。 |
| `AC-017` | core | 所有 M0 公共 HTTP 契约位于 `/api/v1` 并进入 OpenAPI 3.1；已暴露 HTTP 操作的无效输入、权限、租约和幂等冲突返回稳定错误体及可执行恢复信息，尚未公开的 Task/图/冻结领域失败能通过内部适配契约无歧义映射到同一错误目录。 |
| `AC-018` | core | M0 关键操作的成功与失败尝试均产生可查询的不可变审计，包含规定上下文且不泄露密码、令牌、租约秘密或 Workspace 全文。 |
| `AC-019` | core | 现有 Identity、设备配对、Workspace 读取/写入、租约、同步、冲突处理、Web 和 Workspace CLI 核心行为继续通过兼容验证；正式 Task 状态收敛不改变这些已发布接口。 |
| `AC-020` | core | 客户端包不能导入服务端领域或数据库实现；领域规则存在于生产模块并能由 M1/M2 复用，不依赖 UI、原型文本或测试夹具才能执行。 |
| `AC-021` | core | 六类 M0 技术验证均产生明确的通过或替代 ADR 结论；Outbox/Worker 重试保持幂等，SSE 重连使用游标并在过期时重新获取权威资源。 |
| `AC-022` | core | 仓库持续集成可以完成格式、静态检查、构建、类型检查、自动化测试和数据库迁移验证；任一失败会阻止 M0 交付。 |
| `AC-023` | core | Docker/Compose 发布骨架可以完成迁移、启动 API/Worker/Web/Gateway/PostgreSQL，并通过 live/ready 健康检查；无需公共制品发布。 |
| `AC-024` | core | M0 未开放完整 Project/Task 公共 CRUD、正式任务 UI、本地 Workspace 同步或 Agent 写工具；现有公共入口不能借内部测试端口绕过授权和确认。 |
| `AC-025` | core | 深度 20 的任务树、200 节点同级 DAG 和项目级 5,000 活动任务目标不破坏正确性；相关核心操作在参考环境中没有明显卡顿或超时。 |
| `AC-026` | core | 运行时网络与依赖检查证明 API 和 Worker 不调用外部 API、AI 或 LLM，租户过滤、秘密保护和 Workspace 单写者约束没有退化。 |
| `AC-027` | supplemental | 参考服务器上的 200 节点局部 DAG 读取 P95 小于 800 ms；若未达精确目标但 core 证据证明没有明显卡顿、超时或正确性影响，可以记录性能发现项。 |
| `AC-028` | supplemental | 超过主体规模的额外随机树/DAG 种子和并发调度未发现已由 core 证据覆盖行为之外的新异常。 |
| `AC-029` | supplemental | 额外的锁等待、查询计划、SSE 重连 trace 或对象一致检查点诊断能进一步解释实现特征；缺少这些附加诊断不影响已独立证明的 core 结果。 |
